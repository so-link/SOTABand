
# 工作任务详细说明

> 基于 SOTABand 四层架构（应用层 → 核心层 → 资源层 → 存储层）和六大核心子系统（工作流引擎、资源管理、调度算力、多Agent协作、安全治理、可观测性），对 todo-list.md 中各工作任务的内涵进行详细说明。

---

## 1. 平台打包与部署

### 1.1 整体打包运行，跨平台（macOS / Windows / Linux）快速安装部署

**所属子系统**：平台工程（横切面）

**内涵**：将 SOTABand 整体打包为可分发的安装包，支持三大桌面平台的一键安装。包括：(1) Python 后端（FastAPI + uvicorn）及其依赖的自动配置；(2) Node.js 前端（Vite + React）及其依赖的自动配置；(3) 平台相关的路径和权限适配（macOS 的沙盒限制、Windows 的路径分隔符、Linux 的 systemd 服务）；(4) 环境自检脚本（Python ≥ 3.12、Node.js ≥ 20、磁盘空间等）；(5) Docker 容器化部署方案作为备选。目标是让非技术用户也能在几分钟内完成安装并开始使用。

**关联架构**：系统分层中「存储层」的环境配置、「应用层」的前端构建。

## 2. 工具全生命周期

对应架构中「资源生命周期管理子系统」和「资源层 → 工具空间」。工具是 SOTABand 探索式能力增长的核心载体——用户每次探索产生的工具自动沉淀，工具空间持续增长，形成飞轮效应。

### 2.1 工具导出和导入

**所属子系统**：资源生命周期管理（`core/resource/`）→ 工具空间（`resources/tools/`）

**内涵**：实现工具在不同 SOTABand 实例之间的迁移能力。当前工具在本地生成、注册、存储，但缺乏跨实例的导出/导入机制。需要设计标准化的工具包格式（包含 MD 规范文档、Python 代码、依赖声明、版本信息），支持一键导出为压缩包、在另一个实例中导入并自动注册到工具仓库。这是工具空间从「单机孤岛」走向「可流通资产」的关键一步。

**关联架构**：
- 工具空间（`resources/tools/`）：管理工具的元数据、代码存储位置、版本信息
- 资源注册中心（`registry.py`）：导入时自动完成注册登记
- 资源生命周期管理器（`lifecycle.py`）：处理导入时的版本冲突与合并策略

### 2.2 工具跨平台稳定运行

**所属子系统**：调度与算力管理子系统 + 工具空间

**内涵**：确保同一工具在 macOS / Windows / Linux 三个平台上均能正确执行。当前工具代码由 LLM 生成，可能包含平台相关的路径处理、系统调用、依赖库差异。需要：(1) 工具模板中的路径辅助函数（`_resolve_path`）覆盖更多平台边界情况；(2) 依赖安装逻辑适配不同平台的包管理差异（如 Windows 缺少编译工具链时回退到预编译 wheel）；(3) 沙箱执行环境在各平台上的行为一致性保障。

**关联架构**：
- 沙箱引擎（`sandbox.py`）：隔离执行，屏蔽平台差异
- 工具模板（`TOOL_TEMPLATE`）：提供跨平台的路径和系统调用辅助函数

### 2.3 自动调试的效率提高

**所属子系统**：资源生命周期管理子系统 → 资源构建器（`builder.py`）

**内涵**：当前自动调试流程（`_auto_debug_loop`）最多 50 轮迭代，效率有提升空间。优化方向：(1) LLM 分析错误时提供更精准的上下文（如具体的行号、变量值、调用栈），减少试错轮数；(2) 对常见错误模式（ModuleNotFoundError、SyntaxError、TypeError、KeyError）建立分类处理策略，不同类型走不同的修复路径；(3) 引入代码静态分析（AST 检查）在执行前预判潜在问题；(4) 对已成功调试的工具记录调试日志和修复模式，供后续类似工具参考，实现经验复用。

**关联架构**：
- 资源构建器（`builder.py`）：根据需求自动编写代码，是自动调试的入口
- 探索式交互流程：无工具时 → 资源构建器编写代码 → 用户核验 → 注册入库 → 执行

## 3. 安全性

对应架构中「安全与治理子系统」。SOTABand 的核心特征是 LLM 自动生成代码并在沙箱中执行，安全是底线。

### 3.1 代码安全约束

**所属子系统**：安全与治理子系统（`core/security/`）

**内涵**：工具或 Agent 代码中所有涉及本地文件操作、系统调用的，一律只能通过 core 中定义的 API 接口完成。这是对 LLM 生成代码的行为约束——LLM 可能生成任意的文件读写、网络请求、系统命令，必须通过 API 抽象层收口。实现方式：(1) 在 TOOL_TEMPLATE 中只暴露受限的 API 辅助函数（`_call_api`、`_call_tool`、`_resolve_path`）；(2) 代码静态审查时检测直接使用 `open()`、`os.system()`、`subprocess.run()` 等裸调用并拦截；(3) 建立工具代码中可导入模块的白名单机制。

**关联架构**：
- 核心层是「唯一具有执行能力的层次」——所有执行必须经由核心层 API
- API 抽象层：系统核心能力封装为标准 API，工具通过 `_call_api("api-id")` 调用

### 3.2 静态安全审查

**所属子系统**：安全与治理子系统 → 代码核验器（`verifier.py`）

**内涵**：在自动调试中，LLM 每轮生成或修改代码后，在实际执行之前，先进行静态安全分析。检查项包括：(1) AST 级别的危险调用检测（`eval`、`exec`、`compile`、`__import__`、裸 `subprocess` 调用）；(2) 文件路径遍历风险（`../` 越权访问项目目录以外的路径）；(3) 网络请求目标校验（是否访问内网地址、非授权外部服务）；(4) 代码复杂度异常检测（无限循环、递归深度过大、大内存分配）；(5) 导入模块白名单校验。

**关联架构**：
- 代码核验器（`verifier.py`）：自动生成代码后提交用户核验
- 看门狗（`watchdog.py`）：监控异常行为，与静态审查互补形成纵深防御

### 3.3 运行时安全审查

**所属子系统**：安全与治理子系统 → 沙箱引擎（`sandbox.py`）+ 看门狗（`watchdog.py`）

**内涵**：代码在沙箱中执行时，进行实时行为监控。与静态审查互补——静态审查检查代码「写了什么」，运行时审查检查代码「做了什么」。监控维度：(1) CPU 和内存使用上限（防止资源耗尽）；(2) 文件操作审计（读取/写入了哪些路径，是否超出授权目录）；(3) 网络连接监控（发起了哪些网络请求，目标 IP 和端口）；(4) 执行超时自动终止（当前 30 秒，可按工具类型差异化配置）；(5) 子进程链追踪（防止 fork 炸弹等进程爆炸攻击）。

**关联架构**：
- 沙箱引擎（`sandbox.py`）：隔离执行，限制系统资源
- 看门狗（`watchdog.py`）：异常行为检测和自动恢复
- 审计日志（`audit.py`）：记录所有操作，支持事后追溯

## 4. 智能体（Agent）

对应架构中「多智能体协作子系统」和设计理念「一切以 Agent 为主体」。所有处理的最终执行主体都是 Agent，系统本质上是多智能体协作生态系统。

### 4.1 消息路由智能体

**所属子系统**：多智能体协作子系统（`core/agent/`）→ 通信总线（`bus.py`）

**内涵**：构建一个专门的「消息路由智能体」，作为 Web 请求与本地工具之间的桥梁。当外部系统（如 Web 前端、其他微服务）通过 HTTP 请求调用 SOTABand 能力时，路由智能体接收请求，解析意图，在工具空间中匹配合适的工具，调用执行，并将结果返回。这是 SOTABand 从「对话式交互」扩展为「API 式服务」的关键——让工具不仅能通过对话界面手动触发，也能被外部系统以标准 API 方式调用，为后续的平台间集成和自动化工作流打下基础。

**关联架构**：
- 通信总线（`bus.py`）：提供 Pub/Sub 和 RPC 两种通信模式
- 角色协调器（`coordinator.py`）：根据智能体角色和能力进行任务分配

### 4.2 任务编排

**所属子系统**：工作流引擎子系统 + 多智能体协作子系统

**内涵**：智能体不仅要能调用单个工具，还要能将多个工具串联为完整的数据处理流程。当用户描述一个复杂需求时（如「读取 EEG 数据 → 滤波去噪 → 提取频带特征 → 统计分析 → 可视化」），系统自动生成编排描述文件（Markdown 格式），编译为 DAG（有向无环图），由多个 Agent 分工协作执行。任务编排是 SOTABand「复杂模式」的核心，区别于简单需求的「单工具直接调用」。

**关联架构**：
- 意图解析器（`intent_parser.py`）：将自然语言意图解析为标准化流程描述
- 流程编译器（`flow_compiler.py`）：将流程描述编译为可执行 DAG
- 执行器（`executor.py`）：按 DAG 驱动多智能体执行，管理任务生命周期
- 多智能体编排流程：自然语言描述 → 解析 → 编译 → 生成编排文件 → 用户确认 → 执行

### 4.3 智能体代码自动调试

**所属子系统**：多智能体协作子系统 + 资源生命周期管理子系统

**内涵**：Agent 本身也是由代码定义的。参考工具编辑器中已实现的自动调试流程（生成 → 沙箱执行 → LLM 分析错误 → 修复 → 再执行，最多 50 轮），为 Agent 代码建立同样的自动调试能力。Agent 的调试比工具更复杂——因为 Agent 涉及通信、协作、状态管理，需要额外的测试场景构造（如模拟其他 Agent 的消息、模拟任务分配与冲突解决），需要构建 Agent 专属的测试沙箱环境。

**关联架构**：
- Agent 工厂（`factory.py`）：负责 Agent 的实例化和池化管理
- 资源构建器（`builder.py`）：工具代码自动调试的经验可复用到 Agent 调试

### 4.4 智能体独立进程运行

**所属子系统**：多智能体协作子系统 + 调度与算力管理子系统

**内涵**：每个 Agent 在独立的操作系统进程中运行，拥有独立的资源配额和命名空间。好处：(1) 故障隔离——一个 Agent 崩溃不影响其他 Agent；(2) 资源管控——可为不同 Agent 分配不同的 CPU/内存限制；(3) 安全边界——Agent 的文件系统和网络访问可独立配置；(4) 分布式扩展——独立进程天然支持跨机器部署，后续可将 Agent 进程调度到不同算力节点。

**关联架构**：
- Agent 工厂（`factory.py`）：管理 Agent 进程的创建、启动、停止、重启生命周期
- 异构调度器（`heterogeneous.py`）：将 Agent 进程分发到不同算力节点（CPU/GPU/NPU）

### 4.5 智能体通信机制

**所属子系统**：多智能体协作子系统 → 通信总线（`bus.py`）+ 协作协议（`protocol.py`）

**内涵**：建立本地 Agent 间通信和远程 Agent 间通信两套机制。本地通信基于进程间通信（IPC，如 Unix Socket、共享内存），远程通信基于网络协议（如 gRPC / WebSocket）。通信总线提供两种模式：(1) Pub/Sub（发布订阅）——用于事件广播和状态通知；(2) RPC（远程过程调用）——用于请求-响应式的任务委派。协作协议定义统一的消息格式、握手流程、错误处理、超时重试、心跳保活等规范。

**关联架构**：
- 通信总线（`bus.py`）：Pub/Sub + RPC 双模式
- 协作协议（`protocol.py`）：Agent 间交互的消息格式和行为规范
- 角色协调器（`coordinator.py`）：基于通信机制进行任务分配和冲突解决

### 4.6 智能体发布

**所属子系统**：Agent 空间（`resources/agents/`）+ 网络层

**内涵**：用户创建的 Agent 可发布到两种范围：(1) 智能体集市——全局公开，任何用户可发现和使用；(2) 虚拟局部网络——仅团队内成员可见。发布内容包括 Agent 的唯一标识、能力描述（MD 格式）、角色类型、依赖工具列表、协作协议定义等。接收方可浏览 Agent 的能力描述，选择将其添加到自己的 Agent 空间中。这是 Agent 生态从单机走向网络化共享的关键。

**关联架构**：
- Agent 空间（`resources/agents/`）：Agent 定义管理
- 智能体集市（7.5）：全局共享的 Agent 发布平台

## 5. 智能体仓库

对应架构中「资源层 → Agent 空间」。Agent 仓库是 Agent 的全局注册与发现中心，类似工具仓库的概念，采用「仓库 + 工作区」双层架构。

### 5.1 全局智能体仓库

**所属子系统**：资源生命周期管理子系统 → 资源注册中心（`registry.py`）+ 资源发现器（`discoverer.py`）

**内涵**：构建全局的 Agent 注册中心，存储所有可用 Agent 的定义信息（唯一标识、能力描述 MD、角色类型、依赖工具列表、协作协议、健康状态）。用户可从仓库中浏览、搜索 Agent，按需选择 Agent 添加到自己的 Agent 空间（工作区）中。仓库 + 工作区的双层架构与工具空间保持一致——仓库是全局注册表，工作区是当前会话加载的 Agent 子集。

**关联架构**：
- Agent 空间（`resources/agents/`）：管理 Agent 定义
- 资源注册中心（`registry.py`）：统一注册管理，标准化描述
- 资源发现器（`discoverer.py`）：按能力、类型、标签等维度查询和检索

### 5.2 多来源 Agent 发现

**所属子系统**：Agent 空间 + 网络层

**内涵**：Agent 仓库不仅能查看本地已注册的 Agent，还能发现来自「智能体集市」（全局共享）和「虚拟局部网络」（团队内共享）的 Agent。用户可浏览远程 Agent 的能力描述和评价信息，选择将其添加到本地 Agent 空间中（类似工具镜像的概念——下载 Agent 定义到本地，在本地进程中运行）。这是 Agent 生态从单机走向网络化的关键入口。

**关联架构**：
- 智能体集市（7.5）：全局共享的 Agent 发布平台
- 虚拟局部网络（8.2）：团队内的 Agent 共享

## 6. 数据仓库

对应架构中「资源层 → 数据空间」。数据是 SOTABand 多模态处理能力的原材料——支持文本、图像、视频、EEG、fMRI、传感器等多源异构数据。

### 6.1 全局数据仓库

**所属子系统**：资源生命周期管理子系统 + 数据空间（`resources/data/`）

**内涵**：构建全局的数据注册与发现中心，管理所有数据集的元信息（格式、Schema、版本、存储路径、血缘关系、访问权限、质量评分）。用户可从仓库中选择数据集添加到数据空间（工作区）中。与工具仓库不同的是，数据仓库需要处理「数据不实际移动」的场景——大型数据集（如 fMRI 扫描数据可能达到数百 GB）不适宜完整拷贝，需要支持虚拟化访问。

**关联架构**：
- 数据空间（`resources/data/`）：多源异构数据的元数据及存储位置，以及 Memory 和 Result
- 资源注册中心（`registry.py`）：标准化描述，查询获取
- 资源发现器（`discoverer.py`）：按数据类型、格式、标签等维度检索

### 6.2 多来源数据发现

**所属子系统**：数据空间 + 网络层

**内涵**：数据仓库不仅能查看本地数据集，还能发现来自「数据集市」和「虚拟局部网络」的共享数据。对远程数据的访问支持两种模式：(1) 镜像——将数据完整拷贝到本地，适用于中小规模数据集；(2) 虚拟化——数据保留在远端，工具通过网络透明访问，适用于大规模数据集。这是数据虚拟化能力在仓库层面的统一入口。

**关联架构**：
- 数据集市（7.4）：全局共享的数据发布平台
- 数据虚拟化（第 10 节）：镜像和虚拟化两种访问模式的详细设计

## 7. 全局服务器

全局服务器是 SOTABand 从单机走向分布式生态的核心基础设施，负责用户认证、网络管理、三大集市维护。

### 7.1 用户注册与登录

**所属子系统**：用户空间（`resources/users/`）+ 全局服务器

**内涵**：全局服务器提供统一的用户注册和身份认证服务。所有 SOTABand 客户端使用同一套账号体系登录，这是跨实例协作、集市发布和资源访问控制的基础。包括注册（用户名/邮箱/密码）、登录（JWT Token 或 Session）、密码重置、OAuth 第三方登录等标准功能。

**关联架构**：
- 用户空间（`resources/users/`）：用户身份、租户、角色权限、资源配额
- 审计日志（`audit.py`）：记录用户登录和操作

### 7.2 局部网络构建

**所属子系统**：全局服务器 + 用户网络

**内涵**：全局服务器接受用户之间的组网请求，管理虚拟局部网络的创建、成员加入/退出、网络拓扑信息维护。组网后，成员可在网络内共享工具、数据，Agent 之间可跨用户通信协作。全局服务器充当「网络目录」角色——存储网络的成员列表和路由信息，但实际的数据和工具传输在成员之间点对点进行（不经过服务器中转）。

**关联架构**：
- 用户空间（`resources/users/`）：租户和组网关系
- 用户组网（8.2）：成员在网络中共享资源和通信

### 7.3 工具集市

**所属子系统**：全局服务器 + 工具空间（`resources/tools/`）

**内涵**：全局服务器维护一个公共的工具集市，任何用户可将本地工具发布到集市（上传 MD 规范、Python 代码、依赖声明、版本信息、标签）。其他用户可在自己的工具仓库中浏览、搜索集市中的工具，选择获取。集市中的工具只能镜像使用（下载到本地执行），不能虚拟化——因为集市是公开的，发布方不保证持续提供远程执行环境，安全性和可用性无法保障。

**关联架构**：
- 工具空间（`resources/tools/`）：工具的注册、存储
- 工具虚拟化（第 9 节）：工具镜像和虚拟化的实现

### 7.4 数据集市

**所属子系统**：全局服务器 + 数据空间（`resources/data/`）

**内涵**：全局服务器维护一个公共的数据集市，用户可将数据集以「虚拟托管」方式发布到集市——数据仍然留存在用户本地，集市上只登记元信息（名称、类型、格式、规模、描述、标签）和访问地址。其他用户通过数据集市发现数据后，可按发布方允许的模式（镜像下载到本地，或虚拟化在发布方执行工具取回结果）访问数据。虚拟托管模式让数据发布方保持对数据的完全控制权。

**关联架构**：
- 数据空间（`resources/data/`）：数据集的元数据和存储位置
- 数据虚拟化（第 10 节）：虚拟托管、镜像、虚拟化的详细设计

### 7.5 智能体集市

**所属子系统**：全局服务器 + Agent 空间（`resources/agents/`）

**内涵**：全局服务器维护一个公共的 Agent 集市，用户可将自定义 Agent 发布到集市（上传 Agent 定义、能力描述 MD、角色类型、依赖工具列表、协作协议等）。其他用户可发现和获取感兴趣的 Agent。与工具集市类似，Agent 集市中的 Agent 只能镜像到本地使用（下载定义后在本地进程中运行）。

**关联架构**：
- Agent 空间（`resources/agents/`）：Agent 定义管理
- 智能体发布（4.6）：Agent 发布到集市或局部网络

## 8. 用户空间与用户网络

对应架构中「资源层 → 用户空间」。用户是 SOTABand 的操作主体，用户网络是实现分布式团队协作的基础。

### 8.1 用户注册与登录

**所属子系统**：用户空间（`resources/users/`）

**内涵**：建立本地用户身份体系，包括注册、登录、会话管理。用户空间记录用户身份、租户信息、角色权限（管理员/普通用户/访客）、资源配额（工具数量、数据容量、Agent 数量等）、操作审计日志。这是多用户协作和权限管控的前提，也是后续对接全局服务器统一认证的基础。

**关联架构**：
- 用户空间（`resources/users/`）：用户身份、租户信息、角色权限、资源配额、操作审计日志
- 审计日志（`audit.py`）：记录用户操作，支持合规审查

### 8.2 用户组网

**所属子系统**：用户空间 + 网络层

**内涵**：多个用户可组成「虚拟局部网络」，在网络内共享工具、数据，Agent 之间可相互通信协作。这类似于一个私有的团队协作空间——团队成员可以共享自己探索生成的工具和数据集，Agent 之间可以跨用户协作完成更大规模、更复杂的任务。组网是 SOTABand 从「个人工具」走向「团队协作平台」的关键一步，也是工具和数据虚拟化的基础网络设施。

**关联架构**：
- 用户空间（`resources/users/`）：租户和组网关系管理
- 局部网络构建（7.2）：全局服务器接受组网请求
- 工具虚拟化（第 9 节）：在网络内共享和调用远程工具
- 数据虚拟化（第 10 节）：在网络内共享和访问远程数据

## 9. 工具虚拟化

工具虚拟化是 SOTABand 分布式能力的核心——让工具可以跨越物理机器被调用，实现「本地工具」和「远程工具」的统一调用体验。

### 9.1 远程工具管理

**所属子系统**：工具空间（`resources/tools/`）+ 资源发现器（`discoverer.py`）

**内涵**：工具仓库中除了本地工具，还能展示远程可用的工具（来自虚拟局部网络或工具集市）。用户可以查看远程工具的能力描述、输入输出规范、使用评价，决定是否将其添加到本地工具空间中。添加时不一定要下载代码——可以先以虚拟化方式远程调用，验证效果后再决定是否镜像到本地。这是工具仓库从「本地仓库」升级为「全局视图」的关键。

**关联架构**：
- 资源发现器（`discoverer.py`）：跨本地和远程的统合检索
- 工具空间（`resources/tools/`）：本地和远程工具的统一视图

### 9.2 工具镜像

**所属子系统**：工具空间 + 资源生命周期管理

**内涵**：将远程工具完整下载到本地，包括 Python 代码、依赖声明（requirements）、MD 规范文档。镜像完成后，工具的调用方式与本地工具完全一致——在本地沙箱中执行，使用本地的计算资源。系统自动调配运行环境（创建独立 .venv、安装依赖）。工具集市中的工具只能镜像使用（不能虚拟化），因为集市是公开的，发布方不保证持续提供远程执行环境。

**关联架构**：
- 资源构建器（`builder.py`）：镜像后自动调配本地运行环境（创建 .venv、安装依赖）
- 沙箱引擎（`sandbox.py`）：镜像工具在本地沙箱中隔离执行

### 9.3 工具虚拟化

**所属子系统**：工具空间 + 通信总线（`bus.py`）

**内涵**：工具代码中调用远程工具时，不将工具代码下载到本地，而是通过网络将调用请求透明传递到远程工具所在的主机执行，结果返回。底层增加远程工具调用接口（基于通信总线的 RPC 模式），对上层工具代码完全透明——工具开发者只需用 `_call_tool("tool-name", param=value)` 调用，系统自动判断目标工具是本地还是远程，选择本地执行或网络转发。工具集市中的工具不支持虚拟化（只能镜像），虚拟化仅在可信的局部网络内使用。

**关联架构**：
- 通信总线（`bus.py`）：RPC 模式支撑远程工具调用
- 协作协议（`protocol.py`）：定义远程调用的请求/响应格式、超时、错误处理

### 9.4 工具共享

**所属子系统**：工具空间 + 网络层

**内涵**：用户可将本地工具共享给两种范围：(1) 虚拟局部网络——团队内成员可见和使用，支持镜像或虚拟化两种调用方式；(2) 工具集市——全局公开，仅支持镜像方式。共享时需携带工具的完整信息（MD 规范、代码、依赖声明、版本、标签），接收方可在工具仓库中查看并选择使用方式。工具共享是工具生态飞轮效应在网络层的直接体现——一个用户探索生成的工具，可以惠及整个团队乃至全局社区。

**关联架构**：
- 工具空间（`resources/tools/`）：工具的注册、存储、共享元数据
- 工具集市（7.3）：全局共享平台
- 虚拟局部网络（8.2）：团队内共享

## 10. 数据虚拟化

数据虚拟化解决「大数据集不适宜完整拷贝」的场景，与工具虚拟化配合，形成「数据不动，工具动」和「工具不动，数据动」两种互补模式。

### 10.1 数据共享

**所属子系统**：数据空间（`resources/data/`）+ 网络层

**内涵**：用户可将本地数据集共享给两种范围：(1) 虚拟局部网络——团队内成员可见，支持镜像（下载副本）或虚拟化（远程访问）两种方式；(2) 数据集市——全局公开，以虚拟托管方式登记（数据留存在本地，集市只登记元信息）。共享时发布方指定支持的访问模式（仅镜像 / 仅虚拟化 / 两种都支持），以及访问权限（只读 / 可处理）。这是数据资源从「私有」走向「可共享资产」的关键。

**关联架构**：
- 数据空间（`resources/data/`）：数据集的元数据、存储位置、访问权限
- 数据集市（7.4）：全局共享平台
- 虚拟局部网络（8.2）：团队内共享

### 10.2 远程数据管理

**所属子系统**：数据空间 + 资源发现器（`discoverer.py`）

**内涵**：数据仓库中可查看来自虚拟局部网络或数据集市的远程数据集，浏览其元信息（名称、类型、格式、数据规模、描述、标签、发布方、访问模式），选择将其添加到本地数据空间中。这是数据发现和获取的统一入口——用户不需要关心数据物理上在哪里，只需要在仓库中选择需要的数据集。

### 10.3 局部网络数据集镜像

**所属子系统**：数据空间

**内涵**：将团队内共享的远程数据集完整下载到本地存储。镜像完成后，工具调用方式与本地数据完全一致——工具直接通过本地路径读取数据，不感知网络传输。适用于中小规模数据集（MB 到 GB 级别）或需要频繁访问的场景。镜像的数据集会记录数据血缘（来源、版本、同步时间），支持后续增量更新。

### 10.4 局部网络数据集虚拟化

**所属子系统**：数据空间 + 通信总线（`bus.py`）

**内涵**：工具调用远程数据时，不下载数据，而是将本地工具代码镜像到数据所在的主机（服务器端），在服务器端执行，执行结果取回本地。适用于大规模数据集（如 fMRI 扫描数据可达数百 GB）不便传输的场景。这是「工具动，数据不动」的模式——通过网络传输的是工具代码（通常几 KB 到几 MB），而非数据本身。

### 10.5 数据集市虚拟托管

**所属子系统**：数据空间 + 数据集市（7.4）

**内涵**：用户将数据发布到数据集市时，选择「虚拟托管」模式——数据仍然留存在用户本地，数据集市上只登记元信息（名称、类型、格式、规模、描述、标签）和访问地址，由发布方直接提供对外服务。发布方可选：(1) 支持镜像——允许他人下载数据副本；(2) 支持虚拟化——允许他人在发布方环境执行工具，只取回结果。虚拟托管让数据发布方保持对数据的完全控制权，特别适合涉及隐私或合规要求的数据。

### 10.6 数据集市数据集镜像

**所属子系统**：数据空间 + 数据集市

**内涵**：通过数据集市发现目标数据集后，获取发布方地址和访问授权，将数据集从发布方完整下载到本地。镜像后使用方式与本地数据完全一致——工具直接通过本地路径读取。适用于发布方允许镜像访问的数据集，下载完成后不依赖发布方的持续在线。

### 10.7 数据集市数据集虚拟化

**所属子系统**：数据空间 + 数据集市 + 通信总线

**内涵**：通过数据集市发现目标数据集后，获取发布方地址，将本地工具代码镜像到发布方环境运行，执行结果取回本地。这是数据集市场景下的「工具动，数据不动」模式。适用于发布方仅允许虚拟化访问（不允许数据外传）的数据集，或者数据规模过大不适合下载的场景。

## 11. 具体应用场景

SOTABand 的多模态数据处理能力天然适合科研场景，这是 Codex CLI（专注编码）和 WorkBuddy（专注办公）未覆盖的差异化市场。以下应用场景既是目标用例，也是验证平台能力的试金石。

### 11.1 无人机领域

- **11.1.1 图片目标检测模型训练**：基于无人机航拍图片，自动完成数据标注、模型选择、训练配置、训练执行、效果评估的完整工具链。将模型训练流程封装为标准工具，非 AI 专家也能使用。
- **11.1.2 图片目标检测模型部署和发布**：将训练好的模型注册到模型空间，生成对应的调用工具（封装推理接口），发布到工具空间供后续任务使用。
- **11.1.3 训练图片合成**：利用数据增强技术（旋转、裁剪、光照变化、背景替换、噪声注入等）从少量真实样本合成更多训练样本，解决无人机场景中标注数据稀缺的问题。
- **11.1.4 轻量 VLM 大模型的部署和优化**：将视觉语言模型（VLM）部署到边缘设备（无人机机载计算单元），进行模型量化、剪枝、推理优化，适配资源受限环境。
- **11.1.5 线索智能化生成**：从无人机采集的海量航拍数据中，自动识别和标注可疑线索（如异常车辆、人员聚集、建筑物变化），生成结构化的线索报告。
- **11.1.6 样本自动挖掘引擎**：从历史数据中自动挖掘有价值的训练样本（难例样本、边界样本、新类别样本），持续扩充和优化训练数据集。
- **11.1.7 样本质量评估**：对训练样本进行多维度质量打分（图像清晰度、标注准确性、类别多样性、样本代表性），自动过滤低质量样本。
- **11.1.8 照片质量评价**：对无人机拍摄的照片进行自动质量评价（曝光度、对焦清晰度、构图合理性、运动模糊程度、噪声水平等），辅助筛选高质量素材。

### 11.2 医疗工具箱

- **11.2.1 低血氧预测模型：训练与预测**：基于患者连续生理数据（心率、血氧饱和度、呼吸频率、血压等时序数据），训练低血氧事件预测模型，实现提前预警。包含数据预处理、特征工程、模型训练、在线预测的完整工具链。
- **11.2.2 EEG 脑电信号可视化**：读取 EDF/BDF 等标准格式的脑电数据，进行多通道波形可视化、功率谱密度分析、时频分析图谱（spectrogram）绘制、拓扑地形图（topomap）渲染。
- **11.2.3 fMRI 信号可视化**：读取 NIfTI 格式的功能磁共振数据，进行三维脑区激活图渲染、切片视图、时间序列曲线展示，支持多种标准化脑模板（MNI152 等）。
- **11.2.4 fMRI 特征提取**：从 fMRI 数据中提取神经科学常用特征：功能连接矩阵（Functional Connectivity）、ALFF（低频振幅）、ReHo（局部一致性）、fALFF 等，输出为标准格式供后续统计分析。
- **11.2.5 孤独症评估**：基于行为量表（ADOS、ADI-R）、眼动追踪数据、EEG 脑电特征等多模态数据，构建孤独症谱系障碍的辅助评估工具，输出风险评估分数和特征解释。
- **11.2.6 疼痛评估**：基于面部表情分析（视频帧）、生理信号（心率变异性、皮肤电导）等多模态数据，构建疼痛程度自动评估工具，辅助临床疼痛管理。

### 11.3 学术工具箱

- **11.3.1 GitHub 代码查找**：根据研究需求描述，在 GitHub 上搜索相关开源代码仓库，自动分析代码质量、活跃度、文档完整性，输出推荐列表和对比分析。
- **11.3.2 代码复现**：针对论文中描述的算法或方法，辅助进行代码复现——解析论文中的方法描述，在 GitHub 上搜索已有实现，对比评估复现程度，生成复现报告。
- **11.3.3 顶会顶刊论文跟踪**：自动监控指定领域顶级会议（如 NeurIPS、ICML、CVPR）和期刊的最新论文，按关键词和兴趣筛选，生成论文摘要和趋势分析简报。
- **11.3.4 论文撰写**：辅助学术论文撰写——基于研究数据和实验结果，自动生成论文各章节初稿（方法描述、实验结果分析、图表说明），提供语法和学术风格润色。
- **11.3.5 引文检查**：对论文中的参考文献列表进行自动检查——验证每条引文的真实性和准确性（作者、标题、期刊/会议、年份、页码），标记存疑条目。
- **11.3.6 AI 评审**：模拟学术审稿人，对论文进行自动评审——检查逻辑完整性、方法正确性、实验充分性、文献覆盖度，生成评审意见和修改建议。
- **11.3.7 专利查重**：针对待申请专利的技术方案，在专利数据库中检索相关现有专利，进行技术方案对比分析，评估新颖性和侵权风险。
- **11.3.8 专利撰写**：辅助专利文书撰写——基于技术方案描述，自动生成专利申请的各个部分（技术领域、背景技术、发明内容、具体实施方式），确保格式规范。
