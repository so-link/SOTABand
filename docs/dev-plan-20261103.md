>   导入顺序，隐式且脆弱；要么实现，要么删掉入口统一走 `Settings()`。

## 总体判断

平台定位是**个人/小团队自托管 Agent 工作台**，此前提下的取舍（SQLite、JSON registry、
单进程、本机回环信任）不必推翻。真正需要偿还的债务集中且有限：**执行隔离（S1）与对话内
控制信任边界（S2）两条安全线**是「确认 + 审计」叙事成立的前提，优先级最高；其余问题
按「可用性 → 数据一致性 → 可观测性 → 测试」递次安排。S7 类文档漂移已在 2026-11-03
文档审计中修复，不再立项。

## 阶段 P0：安全边界收口（阻断性，先于一切功能扩张）

### P0-1 工具执行 OS 级隔离（S1）

**问题**：`config/settings.py:406` 的 `sandbox_enabled`/`sandbox_type="docker"` 是死配置，
全仓无消费点；工具实际以同用户、全文件系统、继承全部环境变量（含 LLM Key）的裸子进程执行
（`core/executor/tool_executor.py:142-162`），AST 黑名单可被字符串拼接绕过。`code_scan`
是策略而非边界。

**工作项**：
1. 让配置真实生效：`sandbox_type` 至少落地两种实现——docker（有 daemon 时）与 runc/无
   特权降级方案；两者都不可用时**显式警告并拒绝运行未过白名单的工具**，而非静默裸跑。
2. 执行环境最小化：子进程 env 白名单化，LLM Key、平台令牌不再注入工具进程；工具需要
   调 LLM/平台 API 时经既有的 bus/网关通道代理（与 P0-3 汇合）。
3. 降权兜底：docker 不可用时以独立低权用户 + seccomp 运行，文件系统挂载只允许
   `TOOL_DIR` + `storage/` 白名单。

**验收**：故意生成一个 `getattr(os,"sys"+"tem")` 拼接绕过 code_scan 的工具，验证其在
沙箱内无法触达宿主文件系统与 LLM Key；`sandbox_enabled=False` 时启动日志明确降级声明。

**耦合**：与 A-3.3「运行时安全审查」同一子系统，静态审查（3.2）保持为第一道过滤，本项
是最后一道。

### P0-2 对话内控制信任边界闭合（S2）

**问题**：三处泄漏——
① 网关身份取子进程自报的 `user_id`（`core/agent/factory.py:156-160`、
`core/chat_control/gateway.py:44-55` 显式信任 raw），被注入的 Agent 代码可冒充任意用户；
② `InteractiveAgentBase.run_tool` 直通 `ToolExecutor`，不经网关、不落审计
（`core/agent/interactive_base.py:316-321`），确认卡只护 platform 工具；
③ `role="admin"` 全仓无消费点，只读调用以 `role="user"` 构造身份（`gateway.py:156`），
权限模型未闭合。

**工作项**：
1. 身份改由主进程按会话绑定注入：platform_call 帧中的 `user_id` 字段删除或降级为
   校验用回显，网关以工厂登记的会话→用户映射为准。
2. `run_tool` 路径入网关：普通工具至少经网关做审计记账（risk=read 直通但落 `chat_ops`），
   写类工具纳入确认协议；审计不可用时拒绝执行（对齐「结果卡只认审计回执」的文档承诺，
   见 P2-1）。
3. 定义并接通 role 语义：`admin` 消费点落地（系统设置、删除类操作限 admin），或删除
   role 字段不留死枚举——二者取一，不许悬空。

**验收**：单测覆盖「子进程伪造 user_id」「审计写入失败时 platform 调用被拒」两条路径；
`tests/test_chat_control.py` 扩展。

### P0-3 明文密钥收敛（S3）

**问题**：`get_llm_api_config` 返回明文 api_key 且登记为平台工具 `api-llm-get-key`
（`core/api/definitions/api-llm-get-config.md`），LLM 上下文即泄露通道，与 `secrets.py`
脱敏自相矛盾；`file_routes.py:285-412` 可枚举全机目录树；`.env` 无 0600 加固。

**工作项**：
1. 下线 `api-llm-get-key`（或改为只返回掩码视图 + provider/model）；全仓 grep 确认无
   残余调用方。
2. `/scan-directory`、`/browse-directory`、`/list` 收敛到 `storage/` + 项目根白名单
   之内，复用 `chat_control/guards.resolve_allowed_path` 的 realpath 前缀匹配。
3. 写 `.env` 时 `os.chmod(0o600)`；启动自检发现 world-readable `.env` 给 warning。

**验收**：`api-llm-get-key` 从 registry 消失；越界目录请求返回 403 的用例进路由测试。

## 阶段 P1：可用性（不改变单机定位，解除日常卡点）

### P1-1 LLM 并发分池（S4）

**问题**：`core/llm/client.py:38-41` 全局信号量默认 1，任何一次长生成阻塞全部 LLM 调用
（标题摘要、工具匹配排在 20 分钟代码生成之后）。

**工作项**：按调用类别分信号量——`chat`（用户会话）、`gen`（生成/调试，复用
`LLM_GEN_*` 配置线）、`aux`（标题/匹配等轻量调用）三池，池宽进系统设置（扩展 7.6 设置
UI，与 `SettingsView` 现有运行参数区合并）。默认 chat=2 / gen=1 / aux=4。

**验收**：并发发起一次长生成 + 一次对话消息 + 一次标题摘要，三者不再互相串行（以时间戳
断言的集成测试）。

### P1-2 流超时收尾与 Agent 级隔离（S4/S7）

**问题**：`execute_stream` 总超时 `terminate()` 后不向队列放哨兵、直接 return
（`core/agent/factory.py:697-704`），reader 等 EOF，后续请求最长空等 600s 空闲超时。

**工作项**：terminate 后向输出队列投终止哨兵并 cancel reader task；超时事件作为 SSE
`error` 帧透出给前端而非静默悬挂。

**验收**：注入一个死循环 Agent 工具，验证超时后同一 Agent 的下一次请求立即进入新执行。

### P1-3 SSE 断线恢复（S4）

**问题**：前端 SSE 用 POST fetch，`pending_op` 只能恢复确认卡、无法恢复流本身
（`chat_routes.py` 注释确认）。

**工作项**：主进程为每个 run 保留可重放的输出缓冲（带序号），前端重连时携带最后序号
增量续读。缓冲上限按 run 生命周期存在，不落盘。

**验收**：生成中途手动断开网络（或关闭 tab 重开），消息流可续读且不重复。

## 阶段 P2：数据一致性与可观测性

### P2-1 审计写失败不可静默（S6）

**问题**：`audit.record` 失败仅 print 继续（`core/chat_control/audit.py:107-108`），
「结果卡只认审计回执」的不变量无强制；`factory._route_reader`、`bus.deliver`、
`chat_store.set_title` 均静默吞异常。

**工作项**：`audit.record` 改同步落盘 + 失败抛出，网关捕获后按失败语义返回（写类操作
直接拒绝）；reader/bus 的吞异常路径补 `logger.exception`。

### P2-2 SQLite 写路径收敛（S5）

**问题**：chat_store / audit / cron store 各自持单连接 + 进程内 `threading.Lock`，
无跨进程互斥；registry 读-改-写丢失更新；`workspace_tree.json` 整树覆盖写，多标签页
后写覆盖前写。

**工作项**：
1. 三个 store 的写路径收敛到单一 `storage/db.py` 层（一条连接、一个写锁、WAL），
   各模块只持 repository 接口——为未来换 Postgres 留缝，但不迁移。
2. registry 读-改-写加文件锁（`fcntl`/`msvcrt`，json_store 原子替换已有，补互斥即可）。
3. workspace_tree 改 per-tab 读写 + 版本号乐观检查，冲突时提示而非覆盖。

**验收**：两进程并发 register/unregister 无条目丢失（脚本化并发用例）。

### P2-3 结构化日志接线（S6）

**问题**：`config/logging.yaml` 存在但无 dictConfig 消费点；`ObservabilityConfig` 死配置。

**工作项**：`app/main.py` lifespan 里 dictConfig 加载 logging.yaml；死配置项要么接线
要么删除（连同 P0-1 的 sandbox 配置一起清理一遍 settings 中的悬空字段）。
